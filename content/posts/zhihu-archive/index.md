我在知乎写了不少回答和想法。平台的内容随时可能被删除、折叠或迁移，而这些东西是自己花时间写的，应该有一份自己能掌握的副本。于是我搭了一个独立的归档站：

- 归档站：<https://visionjam.github.io/zhihu-archive/>
- 仓库：<https://github.com/visionjam/zhihu-archive>

它和这个博客平行独立：博客继续用来写作，归档站只负责保存和展示。

## 它做什么

同步三类内容：**回答、想法、文章**。每一条生成一个 Markdown page bundle，正文里的图片下载到本地，页面保留知乎原文链接。首次全量、之后增量，中断了可以续跑。

目前同步下来是 100 条内容、75 张图片。想法里的转发也按知乎页面呈现归档（自己的评论加上被引用的原文），不会另外去抓别人的主页。

技术上没有用爬虫框架，也没有模拟浏览器：用本机的知乎登录 Cookie 调网页接口，拿到列表和正文，转成 Markdown，交给 Hugo 构建。Hugo 用的是和博客相同的 PaperMod 主题，所以两边的阅读体验一致。

## Cookie 不出本机

这是整套东西里最重要的约束。

- Cookie 放在用户目录下的单独文件里，不在仓库内，也不在 CI 里。
- GitHub Actions 只做 Hugo 构建和 Pages 部署，没有配置任何 Secret。
- 同步脚本只在本机运行，不打印 Cookie 值；Cookie 失效时明确报错，不会静默失败。
- 图片下载使用独立的、不带 Cookie 的 HTTP 会话。正文里的图片可能来自任意外链，不能把登录态带过去。

推送前还有一道隐私扫描：Cookie/密钥/本机路径/代理配置是硬拦截；电话、邮箱、内网地址这类可能合法出现在技术正文里的内容列为「需确认」。新增或修改的图片会列出来，需要人工确认后才提交。

## 删除的内容也留着

归档站在知乎内容消失后仍然保留页面，并在顶部标注「该内容已从知乎删除」。这是有意的：备份的意义之一就是留住删掉的东西。

如果某条内容后来不想公开了，可以把它加入本机的排除名单，下一轮同步会从站点移除；需要连公开 git 历史一起清除时，还有一个单独的 purge 流程，会先要求确认仓库名，再重写历史并 force-push。它清不掉别人已经 fork 或 clone 的副本，这一点在开始前就想清楚了。

## 几个实际遇到的坑

- 知乎的 App 接口已经对第三方关闭，但网页版自己在用的接口带普通登录 Cookie 仍然可用。
- 文章详情接口会返回 403，但文章列表接口本身已经带回了未截断的全文。所以现在的策略是：列表有正文就直接用，只有正文为空或被截断时才请求详情。这样也顺带减少了请求量。
- 列表里的时间字段不统一：回答用 `created_time`，文章和想法用 `created`。一开始文章日期全变成了 1970 年。
- 知乎正文里有大量 `data:` 开头的懒加载占位图，真实地址在 `data-original` 等属性里。不处理的话，页面里会留下一串 SVG 字符串。

## 边界

这套东西只能保住「第一次同步时还在知乎上」的内容。开始之前就已经删除的，接口找不回来。另外，归档是副本，不是迁移：原文仍然在知乎，归档站只是让它在平台之外也有一份可读、可搜索、可长期保存的版本。

如果你也想做类似的事情，仓库里的 README 记录了完整的运行方式。需要准备的东西只有三样：Python、Hugo，以及一份自己的知乎 Cookie。
